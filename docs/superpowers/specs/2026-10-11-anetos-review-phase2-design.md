# anetos-review 2차 설계: 검증된 수정

- 작성일: 2026-10-11
- 상태: 검토 대기
- 선행: `2026-10-11-anetos-review-phase1-design.md` (1차, 구현 완료)

## 1. 배경과 목표

1차는 리뷰와 기록을 다뤘고, 처음의 세 문제 중 하나가 남아 있다. **리뷰 지적을 고치다가 멀쩡하던 기능이 깨지는 것**이다.

2차는 원장의 지적 하나를 고치는 명령을 추가한다. 목표는 두 가지다.

1. 수정이 다른 것을 깨뜨리면 커밋되기 전에 잡히고 되돌려진다.
2. 고친 문제가 나중에 다시 생기면 테스트가 실패한다. 리뷰 기록이 실행 가능한 검사로 바뀐다.

1차와 같은 원칙을 따른다. 판단은 에이전트가 하고, **통과·실패 판정과 상태 변경은 스크립트가 한다.** 검사가 통과했는지를 LLM이 출력을 읽고 판단하지 않는다.

## 2. 범위

**포함**
- `/anetos-review:review-config`: 검증 명령을 정해 저장한다.
- `/anetos-review:review-fix <ID>...`: 지적을 하나씩 고치고 검증하고 커밋한다.
- `fixer` 에이전트.
- `scripts/fix.mjs`: 검사 실행, 단계별 판정, 범위 확인, 되돌리기, 마무리.
- 1차 `review` 스킬의 작은 변경: 고쳐서 해결된 지적을 에이전트에게 알려 수정을 되돌리자는 지적을 막는다.
- fixture 확장과 측정.

**제외**
- 지적이 없어질 때까지 리뷰와 수정을 자동으로 반복하는 것. 번복과 회귀를 키울 위험이 가장 큰 방식이라 넣지 않는다.
- 여러 지적을 한 커밋으로 묶어 고치는 것.
- 같은 파일 안에서 지적과 무관한 줄을 고쳤는지 LLM으로 판정하는 것. 범위 확인은 파일 단위까지만 한다(7절).
- 테스트 프레임워크별 결과 해석. 검사는 종료 코드로만 본다.
- git 저장소가 아닌 프로젝트. 수정은 git이 있어야 한다. 리뷰는 1차 그대로 git 없이도 된다.

## 3. 구성

```
anetos-review/
├─ skills/
│  ├─ review-config/SKILL.md   # 신규. 사용자만 실행
│  └─ review-fix/SKILL.md      # 신규. 사용자만 실행
├─ agents/
│  └─ fixer.md                 # 신규. 테스트와 수정을 쓴다
└─ scripts/
   ├─ fix.mjs                  # 신규
   └─ fix.test.mjs             # 신규
```

`ledger.mjs`는 원장 상태만 계속 맡는다. 검사 실행과 git 조작은 성격이 달라서 `fix.mjs`로 나눈다. `fix.mjs`는 `ledger.mjs`의 함수를 import해서 원장을 고친다. 외부 의존성은 여전히 없다.

두 스킬 모두 `disable-model-invocation: true`다. 코드를 바꾸고 커밋하는 일은 사용자가 직접 시작해야 한다.

## 4. 검증 설정

대상 저장소의 `.review/config.json`. git으로 추적한다.

```json
{
  "version": 1,
  "checks": [
    { "name": "test", "kind": "test", "command": "npm test", "timeoutSec": 600 },
    { "name": "types", "kind": "static", "command": "npx tsc --noEmit", "timeoutSec": 300 }
  ],
  "testPaths": ["**/*.test.*", "**/*.spec.*", "test/**", "tests/**", "__tests__/**"]
}
```

- `kind`: `test`는 테스트를 실행하는 검사, `static`은 타입체크·린트·빌드처럼 테스트가 아닌 검사.
- `testPaths`: 테스트 파일로 볼 경로. 범위 확인(7절)에 쓴다.
- `checks`는 비어 있어도 된다. 그러면 모든 수정이 "검증 불가"가 된다(6.3).

**`/anetos-review:review-config`의 흐름**
1. `package.json`의 scripts, `Makefile`, `pyproject.toml`, `Cargo.toml`, `go.mod`, CI 설정 등을 읽어 검사 명령 후보를 찾는다.
2. 후보와 `testPaths`를 사용자에게 보여 주고 고칠 것을 묻는다. 사용자가 답하기 전에는 저장하지 않는다.
3. 확정된 내용을 `fix.mjs config set <파일>`로 저장한다. 스크립트가 형식을 검증한다.

설정이 없으면 `review-fix`는 시작하지 않고 `review-config`를 먼저 실행하라고 안내한다.

**알려진 위험.** `config.json`의 명령은 그대로 셸에서 실행된다. 이 파일이 악의적으로 바뀌면 `review-fix`가 그 명령을 실행한다. 프로젝트의 테스트 명령을 실행하는 도구라면 피할 수 없는 성질이다. 완화책으로 `fix.mjs start`가 실행할 명령을 먼저 출력하고, 설정 변경은 git diff에 드러난다.

## 5. 검사 실행과 판정

`fix.mjs`가 `checks`의 명령을 순서대로 실행하고 검사마다 `pass`(종료 코드 0) 또는 `fail`(그 외, 제한 시간 초과 포함)을 기록한다. 출력은 마지막 40줄만 남긴다.

검사 결과는 항상 **기준선과 비교**한다. 기준선은 수정을 시작할 때 아무것도 바꾸지 않은 상태에서 실행한 결과다.

| 기준선 | 현재 | 판정 |
|---|---|---|
| pass | pass | 유지 |
| pass | fail | **회귀** |
| fail | fail | 가려짐 |
| fail | pass | 개선 |

**가려진 검사.** 기준선에서 이미 실패하는 검사는 수정이 무엇을 깨뜨려도 알려 주지 못한다. 시작할 때 어떤 검사가 가려졌는지 보고한다. 가려진 검사는 판정에서 빼고, 남은 검사가 하나도 없으면 "검증 불가"다.

**불안정한 검사.** 회귀로 나온 검사는 한 번 다시 실행한다. 두 번째에 통과하면 회귀로 보지 않고 `flaky`로 표시해 보고에 남긴다.

**한계.** 검사를 종료 코드로만 보므로, 테스트 100개 중 어느 것이 실패했는지는 구분하지 못한다. 기준선에서 테스트 하나라도 실패하면 그 검사 전체가 가려진다.

## 6. `/anetos-review:review-fix`의 흐름

인자는 지적 ID 하나 이상이다. 여러 개면 순서대로 하나씩 처리하고, 하나라도 성공하지 못하면 거기서 멈춘다.

### 6.1 지적 하나의 처리

1. **시작 (`fix.mjs start <ID>`).** 스크립트가 전제 조건을 확인한다.
   - 설정이 있다.
   - 지적의 상태가 `open`이다.
   - 작업 트리가 깨끗하다(`.review/` 제외). 수정의 diff가 다른 변경과 섞이지 않아야 되돌릴 수 있다.
   - 진행 중인 다른 수정이 없다.

   통과하면 기준선을 실행하고, 현재 HEAD와 미추적 파일 목록, 기준선을 `.review/fix.tmp`에 적는다.

2. **테스트 작성.** `fixer`를 `mode: tests`로 띄운다. 넘기는 것은 지적(파일, 심볼, 제목, 근거), 해당 규칙의 설명, `testPaths`뿐이다. fixer는 두 종류의 테스트를 쓸 수 있다.
   - **재현 테스트**: 지적된 문제 때문에 지금은 실패하고, 고치면 통과하는 테스트.
   - **고정 테스트**: 고칠 함수의 현재 동작 중 유지되어야 하는 것을 고정하는 테스트. 그 함수에 테스트가 없을 때 쓴다.

   fixer는 제품 코드를 건드리지 않고, 재현 테스트를 썼는지 여부(`repro: true|false`)와 쓰지 못한 이유를 반환한다. 하드코딩된 비밀 값이나 빠진 제한 시간처럼 실패하는 테스트로 드러내기 어려운 지적은 `repro: false`가 정상이다.

3. **빨강 확인 (`fix.mjs stage red --repro <yes|no>`).** 검사를 실행한다.
   - `repro: yes`이면 `kind: test`인 검사 중 하나 이상이 회귀여야 한다. 회귀가 없으면 재현 테스트가 문제를 재현하지 못한 것이다. fixer에게 한 번 다시 쓰게 하고, 그래도 안 되면 `repro: no`로 내려서 계속한다.
   - `repro: no`이면 어떤 검사도 회귀가 아니어야 한다. 회귀가 있으면 방금 쓴 고정 테스트가 틀린 것이다.
   - `kind: static` 검사는 어느 경우에도 회귀가 아니어야 한다.

4. **수정.** `fixer`를 `mode: fix`로 띄운다. 넘기는 것은 지적과 규칙 설명, 2단계에서 쓴 테스트 파일 목록이다. fixer는 지적된 문제만 고친다.

5. **지적 재확인.** 1차의 `verifier`를 `mode: recheck`로 띄워 지적이 없어졌는지 확인한다.

6. **초록 확인 (`fix.mjs stage fixed --recheck <absent|present>`).** 스크립트가 다음을 모두 확인한다.
   - 어떤 검사도 회귀가 아니다.
   - 재확인이 `absent`다.
   - 바뀐 파일이 허용 범위 안이다(7절).

   검사가 회귀했거나 재확인이 `present`이면 fixer에게 실패한 검사의 출력과 함께 **한 번** 다시 고치게 한다. 두 번째도 실패하면 8단계로 간다. 범위 밖 파일만 문제인 경우는 다시 고치게 하지 않고 7절대로 사용자에게 묻는다.

7. **마무리 (`fix.mjs finish`).** 스크립트가 원장을 고치고(상태 `resolved`, `fixLevel` 기록) 바뀐 파일과 원장(`.review/findings.json`)을 한 커밋으로 만든다. `.review/`의 다른 파일은 커밋하지 않는다. 지금의 파일이 6단계에서 확인한 내용과 다르면 커밋을 거부한다. 커밋 메시지는 `fix(review): <지적 제목> [<지적 ID>]`다.

8. **중단 (`fix.mjs abort`).** 스크립트가 작업 트리를 시작 시점으로 되돌린다. 추적 파일의 변경을 되돌리고, 시작 이후에 생긴 미추적 파일을 지운다. `.review/`의 원장은 건드리지 않고 지적의 `fixAttempts`만 1 올린다. 시작 조건이 "깨끗한 작업 트리"였으므로 되돌려지는 것은 이번 수정이 만든 변경뿐이다.

### 6.2 수정 한 건의 검사 실행 횟수

기준선, 빨강, 초록으로 **최소 3회**, 재시도가 있으면 최대 5회다. 테스트 스위트가 느린 프로젝트에서는 수정 한 건이 오래 걸린다. 2차에서는 이것을 받아들이고, 실제로 문제가 되는지는 써 보고 판단한다.

### 6.3 검증 수준

마무리할 때 수정이 어떤 근거로 검증됐는지를 `fixLevel`로 남긴다.

| 수준 | 조건 | 사람 승인 |
|---|---|---|
| `reproduced` | 재현 테스트가 빨강에서 실패하고 초록에서 통과했다 | 불필요 |
| `guarded` | 재현 테스트는 없지만, 가려지지 않은 검사가 하나 이상 있고 회귀가 없다 | 불필요 |
| `unverified` | 가려지지 않은 검사가 하나도 없다 | **필요** |

`unverified`이면 스킬이 diff를 보여 주고 사용자에게 커밋할지 묻는다. 승인하면 `fix.mjs finish --allow-unverified`, 아니면 `abort`다. 사용자의 답을 받을 수 없는 실행(headless)에서는 묻지 않고 `abort`한다.

**한계.** 재현 테스트가 있는 경우, 함께 쓴 고정 테스트가 수정 전에 통과했는지는 따로 증명되지 않는다. 빨강 단계에서 테스트 검사가 이미 실패 상태이기 때문이다. 고정 테스트를 수정 후의 동작에 맞춰 써 버리는 실수는 이 설계로 잡히지 않는다.

## 7. 범위 확인

`fix.mjs stage fixed`가 git으로 바뀐 파일 목록을 구해 세 가지로 나눈다.

| 분류 | 조건 | 처리 |
|---|---|---|
| 대상 | 지적의 `file` | 허용 |
| 테스트 | 빨강 단계에서 쓴 테스트 파일 | 허용 (수정 단계에서 바뀌면 실패) |
| 범위 밖 | 그 외. 수정 단계에서 손댄 기존 테스트 파일과 새로 만든 테스트 파일 포함 | 중단하고 묻는다 |

범위 밖 파일이 있으면 스킬이 그 파일의 diff를 보여 주고 사용자에게 묻는다. 함수 시그니처가 바뀌어 호출부를 고쳐야 하는 경우처럼 정당한 경우가 있다. 승인하면 `fix.mjs finish --allow-out-of-scope`, 아니면 `abort`다. headless에서는 `abort`한다.

같은 파일 안에서 지적과 무관한 줄을 고쳤는지는 스크립트로 판정할 수 없어서 확인하지 않는다. 이 부분은 fixer의 지침과, 최종 diff가 커밋 하나로 남아 사람이 볼 수 있다는 점에 맡긴다.

## 8. fixer 에이전트

- 도구: Read, Grep, Glob, Edit, Write. 명령 실행 도구는 주지 않는다. 검사를 돌리고 결과를 판정하는 것은 스크립트의 일이다.
- 리뷰 세션의 맥락을 받지 않는다. 지적 하나와 규칙 설명만 받는다.

지침의 핵심:
- 지적된 문제만 고친다. 주변 코드를 정리하거나, 이름을 바꾸거나, 형식을 고치지 않는다.
- 공개 인터페이스(함수 시그니처, 반환 형태, 오류 종류)를 바꾸지 않는다. 바꾸지 않고는 고칠 수 없으면 고치지 말고 그 사실을 반환한다.
- `mode: tests`에서는 제품 코드를, `mode: fix`에서는 2단계의 테스트를 건드리지 않는다. 수정을 통과시키려고 테스트를 고치는 것을 막기 위해서다.
- `.review/` 아래의 파일은 건드리지 않는다.

반환(JSON):
- `mode: tests` → `{ repro: boolean, files: string[], note: string }`
- `mode: fix` → `{ fixed: boolean, files: string[], note: string }`. `fixed: false`이면 스킬은 `abort`한다.

`mode: fix`에서 테스트 파일이 바뀌었는지는 스크립트가 확인한다. 빨강 단계에서 테스트 파일의 해시를 적어 두고 초록 단계에서 비교해, 달라졌으면 실패로 본다.

## 9. 원장과 1차 스킬의 변경

**원장 필드 추가** (`findings.json`의 `version`은 1 그대로. 없는 필드는 없는 것으로 읽는다)
- `fixLevel`: `reproduced | guarded | unverified`. `review-fix`로 해결된 지적에만 있다.
- `fixAttempts`: 중단된 수정 시도 횟수.

상태는 추가하지 않는다. 고쳐서 해결된 지적도 `resolved`다. 나중에 같은 지적이 다시 나오면 1차의 "재발" 경로를 그대로 탄다. 이때 `fixLevel`은 지운다.

**`review` 스킬 변경.** rule-checker와 explorer에게 넘기는 기존 지적 목록에, 범위 파일의 `resolved` 지적 중 `fixLevel`이 있는 것을 "고쳐진 지적"으로 표시해 넘긴다. 두 에이전트의 지침에 다음을 추가한다.

> 고쳐진 지적의 수정을 되돌리자는 지적은 내지 않는다. 고친 방식 자체에 결함이 있으면 그 결함을 구체적으로 지적한다.

A→B로 고친 것을 다음 리뷰가 B→A로 되돌리라고 하는 번복을 막기 위해서다.

## 10. fix.mjs 명령

| 명령 | 동작 |
|---|---|
| `config set <파일>` | 설정 형식을 검증하고 `.review/config.json`에 저장 |
| `config show` | 현재 설정 출력 |
| `start <ID>` | 전제 조건 확인, 실행할 명령 출력, 기준선 실행, 상태 파일 작성 |
| `stage red --repro <yes\|no>` | 검사 실행, 6.1의 3단계 판정, 테스트 파일 해시 기록 |
| `stage fixed --recheck <absent\|present>` | 검사 실행, 6.1의 6단계 판정, 범위 분류 |
| `finish [--allow-unverified] [--allow-out-of-scope]` | 직전 `stage fixed`가 통과였는지 확인, 원장 갱신, 커밋 |
| `abort` | 시작 시점으로 되돌리고 `fixAttempts` 증가 |

모든 명령의 출력은 JSON이다. 판정 결과에는 검사별 판정, 회귀한 검사의 출력 끝부분, 범위 밖 파일 목록, `fixLevel`이 들어 있다.

오류 처리:
- 단계를 건너뛴 호출(`start` 없이 `stage`, 통과하지 않은 `stage fixed` 뒤의 `finish`)은 오류로 끝낸다.
- 필요한 승인 플래그 없이 `finish`를 부르면 오류로 끝낸다.
- `finish`의 커밋이 실패하면(커밋 훅 실패 등) 원장을 `finish` 이전으로 되돌리고 오류를 낸다. 작업 트리는 그대로 두어 사용자가 원인을 볼 수 있게 한다.
- `abort`는 상태 파일이 없으면 아무것도 하지 않는다.

## 11. 검증

**단위 테스트 (`fix.test.mjs`)**

임시 git 저장소를 만들어 실제로 실행한다. 검사 명령은 `node -e "process.exit(0)"`처럼 결과를 정할 수 있는 것을 쓴다.

- 5절의 판정 표 네 경우와, 가려진 검사만 있을 때 `unverified`가 되는 것.
- 회귀한 검사가 재실행에서 통과하면 `flaky`가 되고 회귀로 세지 않는 것.
- 제한 시간을 넘긴 검사가 `fail`이 되는 것.
- `start`가 더러운 작업 트리, `open`이 아닌 지적, 설정 없음, 진행 중인 수정을 거부하는 것.
- `stage red`: `repro yes`인데 회귀가 없으면 실패, `repro no`인데 회귀가 있으면 실패.
- `stage fixed`: 회귀, 재확인 `present`, 범위 밖 파일, 테스트 파일 변조를 각각 잡는 것.
- `finish`가 승인 플래그 없이 `unverified`와 범위 밖 파일을 거부하는 것, 커밋이 지적 ID를 담는 것, 원장이 `resolved`와 `fixLevel`을 갖는 것.
- `abort` 뒤에 `git status`가 시작 시점과 같고, 시작 전부터 있던 미추적 파일이 남아 있으며, `.review/`가 보존되는 것.
- 커밋 실패 시 원장이 되돌려지는 것.

**측정 (fixture 확장)**

`fixtures/sample-repo`에 `node:test` 테스트를 추가한다. 일부 함수만 덮고 나머지는 비워 둔다. 함정을 둘 넣는다.
- 가장 단순한 수정이 다른 함수의 기존 테스트를 깨뜨리는 지적 하나.
- 호출부를 함께 고쳐야만 고칠 수 있는 지적 하나.

1차 측정으로 원장에 지적이 등록된 상태에서 `review-fix`를 지적마다 실행한다.

| 지표 | 세는 방법 | 초기 목표 |
|---|---|---|
| 회귀를 남긴 커밋 | 커밋된 수정마다 그 시점에서 전체 검사를 실행해 기준선 대비 회귀가 있는 수 | 0건 |
| 범위 밖 무단 변경 | 승인 없이 대상·테스트 밖 파일이 커밋된 수 | 0건 |
| 첫 번째 함정 | 깨지는 수정이 커밋되지 않았다(다르게 고쳐 통과했거나 중단됨) | 충족 |
| 두 번째 함정 | 범위 밖 파일로 멈추고 물었다 | 충족 |
| 수정 후 리뷰 | 전부 고친 뒤 `/review`를 돌렸을 때, 수정을 되돌리자는 신규 지적 수 | 0건 |
| 커밋된 수정 | 지적 중 커밋까지 간 수(참고) | 목표 없음 |
| `reproduced` 비율 | 커밋된 수정 중 재현 테스트로 검증된 수(참고) | 목표 없음 |

1차와 같이, 목표에 못 미치면 원인을 찾아 고치되 fixture를 쉽게 바꾸거나 세는 방법을 바꾸지 않는다.

## 12. 미결 사항

- **커밋을 기본 동작으로 둘지.** 이 설계는 수정마다 자동으로 커밋한다. 다음 수정이 깨끗한 작업 트리를 요구하고, 수정 하나가 커밋 하나여야 나중에 되돌리기 쉽기 때문이다. 커밋 없이 변경만 남기는 방식을 원하면 6.1의 7단계와 "깨끗한 작업 트리" 조건을 다시 설계해야 한다.
- **느린 테스트 스위트.** 수정 한 건에 검사를 3~5회 실행한다. 감당하기 어려운 프로젝트가 나오면 검사별로 "빠른 변형" 명령을 두는 것을 검토한다.
- **파일 단위 범위 확인의 한계.** 같은 파일 안의 무관한 변경은 잡지 못한다. 측정에서 실제로 발생하는지 본 뒤 필요하면 다룬다.

## 13. 최종 리뷰 뒤에 바뀐 것 (2026-10-11)

구현을 새 컨텍스트에서 검토한 결과, 검증된 내용과 실제 커밋되는 내용이 어긋날 수 있는 경로가 여럿 나왔다. 아래와 같이 고쳤고, 위 본문과 다른 부분은 이 절이 우선한다.

- **시작 조건 추가.** 지적의 파일이 git에 추적되지 않으면 시작하지 않는다(되돌릴 기준이 없다). git 저장소의 최상위 폴더가 아니면 시작하지 않는다.
- **설정 고정.** 시작할 때의 설정을 상태 파일에 담아 끝까지 쓴다. 도중에 `config.json`이 바뀌어도 판정 기준은 바뀌지 않는다.
- **"수정이 바꾼 파일"의 정의.** 파일 이름이 아니라 내용 해시로 본다. 시작 전부터 있던 미추적 파일과, 검사가 실행 중에 만들거나 고친 파일은 수정과 무관한 것으로 기록한다. 원래 있던 미추적 파일을 수정이 바꾸면 범위 밖으로 잡힌다.
- **`abort`의 한계 보고.** 원래 있던 미추적 파일을 수정이 바꾼 경우는 원본이 없어 되돌릴 수 없다. `abort`가 그 파일을 `unrestored`로 알린다.
- **아무것도 고치지 않은 수정 거부.** 테스트 외에 바뀐 파일이 없으면 `stage fixed`가 `nothing-fixed`로 실패한다.
- **제한 시간 초과 시 프로세스 정리.** 셸만이 아니라 그 아래 프로세스까지 끝낸다.
- **파일 이름을 그대로 취급.** 대괄호 등이 든 이름이 glob으로 해석되어 다른 파일을 커밋에 끌고 들어가지 않는다.
