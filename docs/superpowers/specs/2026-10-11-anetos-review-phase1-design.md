# anetos-review 1차 설계: 일관된 리뷰 + 기록

- 작성일: 2026-10-11
- 상태: 검토 대기
- 범위: 1차(리뷰와 기록). 2차(검증된 수정)는 개요만 싣고 별도 스펙으로 쓴다.

## 1. 배경과 목표

이전에 만든 코드리뷰 플러그인들에서 세 가지 문제가 있었다.

1. 돌릴 때마다 다른 문제점이 잡힌다.
2. 코드 회귀가 일어난다. 구체적으로는 (a) 리뷰 지적을 고치다가 다른 기능이 깨지고, (b) 이전 리뷰가 A→B로 바꾸라고 한 것을 다음 리뷰가 B→A로 되돌리라고 한다.
3. 리뷰 결과와 해결 내용이 남지 않아 같은 논의가 반복된다.

LLM 리뷰를 "같은 코드에 항상 같은 결과"로 만들 수는 없다. 이 설계의 목표는 **수렴**이다. 한 번 판정된 것은 다시 흔들리지 않고, 재실행하면 새 발견만 추가된다.

문제별로 쓰는 장치는 다음과 같다.

| 문제 | 장치 | 단계 |
|---|---|---|
| 매번 다른 지적 | 고정 규칙 검사, 기존 지적의 예/아니오 재확인, 후보 검증 | 1차 |
| 리뷰 번복 (2b) | 결정 기록과 재검토 요청 분리 | 1차 |
| 기록 부재 | `.review/` 원장 | 1차 |
| 수정이 다른 것을 깨뜨림 (2a) | 수정 관문 | 2차 |

## 2. 범위

**1차에 포함**
- `/review`: 규칙 검사, 자유 탐색, 검증, 원장 갱신, 보고
- `/review-decide`: 사람의 결정 기록
- 대상 저장소의 `.review/` 저장 구조
- 원장 조작 스크립트와 그 단위 테스트
- 수렴을 측정할 fixture 저장소

**1차에서 제외**
- 코드 수정 (`/review-fix`, 2차)
- 나중에 추가할 mod
- 파일 이름 변경 추적 (4.3의 알려진 한계)
- CI 연동, PR 코멘트 게시

## 3. 폴더 구조

플러그인은 `C:\dev\anetos\anetos-review\` 안에 둔다. 저장소 루트에는 나중에 mod가 형제로 추가된다.

```
anetos/
├─ docs/superpowers/specs/          # 스펙 문서
└─ anetos-review/
   ├─ .claude-plugin/plugin.json
   ├─ skills/
   │  ├─ review/SKILL.md            # /review 진행 절차 (오케스트레이터)
   │  └─ review-decide/SKILL.md     # 결정 기록
   ├─ agents/
   │  ├─ rule-checker.md            # 규칙별 판정
   │  ├─ explorer.md                # 규칙 밖 후보 탐색
   │  └─ verifier.md                # 후보 검증, 기존 지적 재확인
   ├─ rules/default.md              # 기본 규칙
   ├─ scripts/
   │  ├─ ledger.mjs                 # 원장 조작 (의존성 없는 Node)
   │  └─ ledger.test.mjs            # node --test 로 실행
   └─ fixtures/sample-repo/         # 문제를 심어 둔 측정용 저장소
```

루트를 마켓플레이스로 구성할지 여부는 mod를 추가할 때 정한다. 1차에서는 `anetos-review/` 하나만 플러그인으로 동작하면 된다.

## 4. 대상 저장소의 저장 구조

리뷰 대상 저장소의 루트에 `.review/`를 만들고 git으로 추적한다. 코드와 같은 커밋 히스토리를 타야 지적이 어느 커밋에서 생기고 해결됐는지를 따질 수 있다.

| 파일 | 내용 | 쓰는 주체 |
|---|---|---|
| `rules.md` | 검사 규칙. 첫 실행 때 `rules/default.md`를 복사하고 이후 프로젝트가 고친다 | 사람 |
| `findings.json` | 지적 원장 | `ledger.mjs`만 |
| `decisions.md` | 결정과 이유 | `ledger.mjs`만 (추가 전용) |

### 4.1 rules.md

규칙 하나가 섹션 하나다.

```markdown
## R-001 외부 입력을 검증 없이 쿼리에 넣지 않는다
- 적용: src/**/*.ts
- 설명: ...
- 위반 예: ...
```

규칙 ID는 한 번 부여하면 바꾸지 않는다. 규칙을 없앨 때는 삭제하지 않고 `- 상태: 폐기`를 붙인다. ID를 재사용하면 원장의 과거 지적이 다른 규칙을 가리키게 된다.

### 4.2 findings.json

```json
{
  "version": 1,
  "findings": [
    {
      "id": "F-3a9c1e07",
      "source": "R-001",
      "file": "src/db/user.ts",
      "symbol": "findUserByName",
      "title": "name 파라미터가 검증 없이 쿼리 문자열에 들어감",
      "evidence": "src/db/user.ts:42",
      "status": "open",
      "firstSeen": "<커밋 해시>",
      "lastChecked": "<커밋 해시>",
      "decisionId": null
    }
  ]
}
```

- `source`: 규칙 ID, 또는 자유 탐색에서 온 경우 `explore:<분류>` (분류는 `bug`, `security`, `data-loss`, `concurrency` 중 하나).
- `evidence`의 줄 번호는 참고용이며 ID 계산에 쓰지 않는다.

### 4.3 지적 ID

`F-` + `sha1(source | file | symbol)`의 앞 8자리.

- 줄 번호는 코드가 조금만 바뀌어도 달라지므로 쓰지 않는다.
- `symbol`은 지적이 속한 가장 가까운 함수·클래스·최상위 선언의 이름이다. 어느 것에도 속하지 않으면 `<module>`.
- 알려진 한계: 파일이나 심볼의 이름이 바뀌면 다른 지적으로 취급된다. 1차에서는 받아들이고, 재확인 단계에서 기존 지적은 "해결됨"으로, 새 위치의 것은 신규로 잡힌다.

### 4.4 상태 전이

```
(신규) ──> open ──┬──> resolved        재확인에서 "더 이상 없음"
                  ├──> intended        사람 결정: 의도된 설계
                  └──> rejected        사람 결정: 지적이 틀림

(후보) ──> dismissed                   verifier 검증 실패

intended / rejected ──> reopen-requested   결정 이후 파일이 바뀌었고 같은 지적이 다시 나옴
reopen-requested ──┬──> open           사람이 재검토 승인
                   └──> (이전 상태)    사람이 재검토 거부

resolved ──> open                      같은 지적이 다시 발견됨 (재발)
```

- `reopen-requested`로 바꿀 때 이전 상태를 `previousStatus` 필드에 남겨, 거부 시 그 상태로 되돌린다.
- **결정 고정.** `intended` / `rejected` / `keep` 결정을 기록할 때 그 지적의 파일 내용 해시를 `decidedHash` 필드에 남긴다(줄바꿈은 LF로 맞춘 뒤 계산). 다음 리뷰에서 같은 지적이 다시 나와도 파일 해시가 그대로이면 상태를 바꾸지 않고 요약의 `decided` 묶음에만 넣는다. 해시가 달라졌을 때만 `reopen-requested`가 된다. `intended` 결정은 위반이 있다는 것을 이미 알고 내린 것이므로, 코드가 그대로인데 다시 묻는 것은 같은 논의의 반복이다. (2026-10-11 수렴 측정에서 매 실행마다 재검토 요청이 반복되는 것을 확인하고 추가했다.)
- 알려진 한계: 해시는 심볼이 아니라 파일 단위다. 같은 파일의 다른 함수만 고쳐도 그 파일의 결정된 지적은 한 번 재검토 요청이 된다. `keep`으로 답하면 새 내용 기준으로 다시 고정된다.
- `decidedHash`가 없는 지적(이 기능 이전에 결정된 것, 결정 당시 파일이 없던 것)은 다시 나오면 `reopen-requested`가 된다.

- `dismissed`도 원장에 남긴다. 같은 후보가 다시 올라오면 ID가 일치하므로 검증을 반복하지 않고 버린다.
- `resolved`였던 지적이 다시 발견되면 `reopen-requested`가 아니라 바로 `open`으로 돌린다. 이것은 번복이 아니라 실제 재발이므로 보고에서 "재발"로 따로 표시한다.
- 허용되지 않은 전이를 요청하면 `ledger.mjs`가 오류로 끝낸다.

### 4.5 decisions.md

```markdown
## D-0001
- 날짜: 2026-10-11
- 지적: F-3a9c1e07
- 대상: src/db/user.ts findUserByName
- 결정: intended
- 이유: 호출부가 전부 내부 상수만 넘기며, 이 함수는 외부에 노출되지 않는다.
```

추가 전용이다. 결정을 뒤집을 때도 기존 항목을 고치지 않고 새 항목을 추가한다.

## 5. `/review` 흐름

오케스트레이터는 `skills/review/SKILL.md`를 따르는 메인 세션이다. 판단은 서브에이전트가 하고, 원장은 메인이 `ledger.mjs`로만 건드린다.

1. **범위 확정.** 인자가 없으면 기준 브랜치 대비 diff의 변경 파일, 경로를 주면 그 경로의 파일. `.review/`가 없으면 `ledger.mjs init`으로 만들고 계속한다.
2. **불러오기.** `rules.md`, `decisions.md`, 범위 파일에 걸린 기존 지적(`ledger.mjs list --files ...`).
3. **기존 지적 재확인.** 범위 파일의 `open` 지적마다 verifier에게 "이 지적이 현재 코드에 아직 있는가"를 묻는다. 답은 `present` / `absent`와 근거 위치.
4. **규칙 검사.** rule-checker가 `적용` glob에 맞는 규칙과 파일을 받아 규칙마다 `violation` / `pass` / `n/a`를 판정한다. `violation`에는 파일, 심볼, 근거 위치가 붙는다.
5. **자유 탐색.** explorer 하나가 규칙에 없는 문제 후보를 낸다. 분류는 4.2의 네 가지로 제한한다. 스타일이나 취향에 관한 후보는 내지 않는다.
6. **후보 검증.** 후보마다 verifier가 코드와 주장만 받아(explorer의 추론은 전달하지 않는다) 구체적인 실패 시나리오를 댈 수 있는지 판정한다. `confirmed`만 지적이 되고 나머지는 `dismissed`로 기록한다. 원장에 같은 ID가 `dismissed`로 이미 있으면 검증 없이 버린다.
7. **기존 지적과의 매칭.** 4·6단계의 에이전트는 담당 파일의 기존 지적 목록(ID, source, symbol, title)을 받고, 각 결과에 `matches: <기존 ID>` 또는 `matches: null`을 적는다. 메인은 `matches`가 있으면 그 ID를, 없으면 계산한 ID를 쓴다.
8. **결정 충돌 검사.** 결과의 ID가 원장에서 `intended` / `rejected` 상태면 일반 지적으로 올리지 않는다. 결정 이후 파일이 그대로이면 아무것도 바꾸지 않고(4.4의 결정 고정), 파일이 바뀌었으면 `reopen-requested`로 바꾼다. 코드 수정을 권하지 않는다.
9. **원장 갱신.** 모든 결과를 하나의 JSON으로 모아 `ledger.mjs apply`에 넘긴다.
10. **보고.** 다음 다섯 묶음으로 나눠 보여 준다: 신규 / 여전히 open / 해결됨 / 재발 / 재검토 요청. 각 항목에 ID를 붙인다. 결정이 유지된 지적(`decided`)과 기각된 후보(`dismissed`)는 개수만 알린다.

### 5.1 서브에이전트 사용 규칙

- **반환 형식은 JSON으로 고정한다.** 자유 서술로 받으면 메인이 옮기는 과정에서 내용이 바뀐다.
  - rule-checker: `[{ruleId, file, symbol, verdict, evidence, title, matches}]`
  - explorer: `[{category, file, symbol, claim, evidence, matches}]`
  - verifier(후보): `{verdict: "confirmed"|"unconfirmed", scenario, evidence}`
  - verifier(재확인): `{verdict: "present"|"absent", evidence}`
- **필요한 것만 넘긴다.** 각 에이전트에는 담당 규칙, 담당 파일, 그 파일의 기존 지적 목록만 준다.
- **원장을 직접 쓰지 않는다.** 에이전트끼리는 서로의 결과를 볼 수 없어서, 각자 쓰면 같은 문제가 다른 ID로 중복 등록된다.
- **explorer는 하나만 띄운다.** 여러 개를 띄우면 발견은 늘지만 실행마다의 변동도 커진다.
- **분할 기준.** 범위 파일이 10개 이하이면 rule-checker 하나, 넘으면 디렉터리 기준으로 10개 이하 묶음으로 나눠 병렬 실행한다. 재확인과 후보 검증은 건마다 독립이므로 병렬로 돌린다. 10이라는 값은 초기값이며 7절의 측정 결과로 조정한다.

## 6. `/review-decide`

```
/review-decide <지적 ID> <intended|rejected|reopen|keep> "이유"
```

- `intended`, `rejected`: `open` 지적에 대한 결정.
- `reopen`, `keep`: `reopen-requested` 지적에 대한 승인과 거부.
- 이유는 필수다. 비어 있으면 스크립트가 거부한다.
- `ledger.mjs decide`가 `findings.json`의 상태를 바꾸고 `decisions.md`에 항목을 추가한다.

## 7. ledger.mjs

의존성 없는 Node 스크립트 하나다. 대상 저장소 루트에서 실행한다.

| 명령 | 동작 |
|---|---|
| `init` | `.review/`를 만들고 `rules/default.md`를 `rules.md`로 복사, 빈 원장 생성. 이미 있으면 아무것도 하지 않는다 |
| `list [--files a,b] [--status s]` | 조건에 맞는 지적을 JSON으로 출력 |
| `id <source> <file> <symbol>` | 지적 ID 계산 |
| `apply <결과 파일>` | 재확인·규칙 검사·검증 결과를 원장에 병합하고, 변화 요약(신규/유지/해결/재발/재검토 요청)을 JSON으로 출력 |
| `decide <id> <결정> --reason "..."` | 상태 전이와 결정 기록 |

오류 처리:
- `findings.json`이 깨졌거나 `version`이 다르면 아무것도 쓰지 않고 오류로 끝낸다.
- `apply`의 입력이 5.1의 형식에 맞지 않으면 어느 항목이 왜 틀렸는지 출력하고 원장을 건드리지 않는다.
- 쓰기는 임시 파일에 쓴 뒤 이름을 바꾸는 방식으로 한다.

## 8. 검증

**단위 테스트 (`ledger.test.mjs`)**
- 같은 입력에 같은 ID가 나오고, 줄 번호만 다른 입력에도 같은 ID가 나온다.
- 4.4의 모든 허용 전이가 동작하고, 허용되지 않은 전이는 오류가 난다.
- `apply`를 같은 결과로 두 번 실행해도 원장이 달라지지 않는다.
- `dismissed` 후보가 다시 들어오면 신규로 잡히지 않는다.
- `intended` 지적과 같은 ID의 위반이 들어오면, 결정 이후 파일이 바뀐 경우에만 `reopen-requested`가 되고 그대로이면 상태가 유지된다.
- 깨진 원장과 형식이 틀린 입력에서 원장이 변하지 않는다.

**수렴 측정 (`fixtures/sample-repo`)**

규칙 위반 5건과 규칙 밖 버그 3건을 심은 작은 저장소에 `/review`를 코드 변경 없이 3회 연속 실행한다.

| 지표 | 초기 목표 |
|---|---|
| 심은 규칙 위반 중 1회차에 잡힌 수 | 5건 중 5건 |
| 2·3회차에 같은 문제가 다른 ID로 중복 등록된 수 | 0건 |
| 2·3회차의 신규 지적 수 | 회차당 2건 이하 |
| `intended`로 결정한 지적이 일반 지적으로 다시 올라온 수 | 0건 |

목표값은 초기 기준이다. 미달하면 원인을 찾아 설계를 고치고, 목표값 자체가 비현실적인 것으로 드러나면 근거와 함께 스펙을 고친다. 중복 등록이 0이 아니면 5절 7단계의 매칭이 실패한 것이므로 가장 먼저 본다.

## 9. 2차 개요: 검증된 수정

`/review-fix <ID>`를 추가한다. 세부 설계는 1차를 써 본 뒤 별도 스펙으로 쓴다.

- 첫 실행 때 검증 명령(테스트, 타입체크, 린트, 빌드)을 탐지해 `.review/config.json`에 고정하고 사람 확인을 받는다.
- 수정 전에 검증을 돌려 기준선을 잡고, 이미 실패하는 항목은 따로 표시한다.
- 지적 하나당 수정 하나. 지적된 파일·심볼 밖의 diff가 나오면 중단하고 묻는다.
- 테스트가 없는 영역은 현재 동작을 고정하는 테스트를 먼저 쓰고, 불가능하면 "검증 불가"로 표시해 사람 승인을 받는다.
- 수정 후 검증이 통과하면 지적 ID를 담아 커밋하고, 실패하면 수정을 되돌린다.

## 10. 미결 사항

- 저장소 루트의 구성(마켓플레이스 여부): mod를 추가할 때 정한다.
- `rules/default.md`에 넣을 기본 규칙 목록: 구현 계획 단계에서 정한다. 언어에 무관한 규칙 10개 안팎으로 시작한다.
